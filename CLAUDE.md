# LocalBoard: handoff notes for Claude Code

This file summarizes the work done so far in a claude.ai session, so you can continue it. Claude Code reads it automatically at the start of every session in this repo. `README.md` is the user-facing guide; this file covers status, design and open issues.

## What the user asked for

An Android keyboard similar to Gboard that does **everything locally**: swipe typing, autocorrect, and improving from usage patterns, all on the device. The user's answers to the initial questions:

- **Platform:** Android
- **Delivery:** a ready-to-install APK; the user will not build it themselves
- **Language:** English only
- **Extras for v1:** an emoji panel and themes/dark mode (no clipboard history)
- **Added later:** settings for individual behaviors, e.g. "whether backspace undoes an autocorrect" and "whether double space makes a period"

## Status

- **Built by GitHub Actions** (`.github/workflows/build.yml`) on every push and pull request; pushes to `main` publish the APK as a GitHub Release named `build-N`. That is how the user installs it. Cloud sessions here cannot reach Google's Maven/SDK hosts, so a local `./gradlew` build fails; use CI.
- **Run on an emulator** by `.github/workflows/screenshots.yml`: it installs the debug build, makes it the active keyboard, drives it with injected touches (`app/src/androidTest/java/dev/localboard/shots/ShotRunner.java`, platform APIs only, no test libraries) and force-pushes the PNGs to the `screenshots` branch. Fetch that branch to look at them.
- **Logic tests:** `tools/run_tests.sh` (JDK + Python 3 only) runs 44 typing scenarios against the real service and the accuracy simulation. CI runs it too.
- **Not yet run on a real phone.** On-device speed, haptics and real-finger swipe accuracy are unverified.
- To compile against the real Android API without the SDK, Robolectric's `org.robolectric:android-all` jar from Maven Central works as a classpath (`javac --release 17 -cp android-all.jar ...`). It includes hidden APIs, so it is more permissive than `android.jar`.

### Workflow

1. Run `tools/run_tests.sh` after changes to the engine or the keyboard service.
2. Push; check both workflows; look at the screenshots branch for anything visual.
3. Debug builds log `LBGEOM <x> <y> <w> <h> <unit> <rowH> <stripH>` from `KeyboardView` so the screenshot driver can find the keys; release builds don't.

## How the engine works

**Coordinates:** everything is in key widths. The view converts pixels, and `KeyboardView.buildGeometry()` produces the real letter-key centers.

**Tap decoding (`TapDecoder`):**
- Score = log prior (dictionary frequency mixed with personal usage) + bigram context − alignment cost.
- The alignment is a weighted Damerau–Levenshtein over the taps:
  - **Substitution:** a Gaussian touch model, σ = 0.5 key width, capped at 9. It is centered on the key center plus the user's learned offset for that key.
  - **Insert:** 4, or 1.5 if the same key was tapped twice in a row.
  - **Delete:** 4, or 1.5 for a doubled letter, 0.1 for an apostrophe (so "dont" becomes "don't").
  - **Transposition:** 1.5.
- **Completions:** a prefix cost plus 0.25 per remaining letter.
- **Candidate search:** words starting with the first tap's letter or its neighbors (substitution cost < 3), or with the second tap's letter for 3+ letter words (to catch swapped first letters). Alignments are cut off early once a word can no longer make the top-8 lists.
- **When it autocorrects:**
  - If the typed word is known, the best alternative must beat it by 5.0 in score.
  - If the typed word is unknown, the best candidate's cost must be ≤ 2 + 1.1 × length.
  - Offensive words are never offered unless the user turns that setting off; words the user typed themselves are still learned.

**Swipe decoding (`SwipeDecoder`):**
- **Filter:** the first letter must be within 1.4 key widths of where the path starts, and the last letter within 1.6 of where it ends.
- **Letter cost:** an order-preserving alignment of the word's distinct consecutive letters to 64 resampled path points. The first and last letters are pinned to the endpoints with weight `endWeight` = 2.
- **Shape cost:** the path resampled to 32 points and compared point by point with the ideal key-center path (`shapeWeight` = 12, σ = 0.6).
- **Length penalty:** 3 × (log of the path length ratio)².
- **Total:** prior + context − costs. Branch-and-bound against the current top-5.

**Learning (`UserModel`, all local):**
- **Counts:** per-word use counts. A word outside the dictionary becomes "known" (never autocorrected away) after 2 uses or one explicit confirmation: picking it from the bar, or restoring it with backspace-undo.
- **Next-word data:** bigram counts, capped at 60 followers per word. A next-word prediction appears once a pair has been used twice.
- **Tap offsets:** a running average per key, clamped to ±0.35 key widths. They're learned only from committed words that are known and whose length matches the taps.
- **Where learning is off:** password, email, URL and filter fields, `IME_FLAG_NO_PERSONALIZED_LEARNING` (incognito) fields, and whenever the "Learn" setting is off.
- **Storage:** saved to `filesDir/user_model.tsv` (written atomically via a temp file and rename) every 25 learned words and whenever the keyboard closes.
- **Capitals:** a capital that came only from sentence-start auto-caps is stored lowercase; a manual capital on an unknown word is kept (names).

**Composing model (`LocalKeyboardService`):**
- **Typing:** the current word is composing text. Space, punctuation, enter, or a suggestion tap commits it, autocorrecting if allowed.
- **Undo:** backspace right after an autocorrect restores the typed word only if the text before the cursor is exactly "correction + separator". It then unlearns the correction and confirms the original.
- **Swiping:** a swiped word stays composing so a suggestion tap can swap it, and a pending space goes in before the next word. One backspace deletes the whole swiped word.
- **Stale cursor reports:** `onUpdateSelection` checks the actual text before dropping the composing word, because the app's cursor reports can lag behind fast typing.

## Correcting committed words (`LocalKeyboardService`)

- **Reopening:** backspace at the end of a word, or typing right after one, turns it back into the composing word (`reopenWordBeforeCursor`); a selected whole word being retyped works the same. The word as it was is kept in `resumeOriginal`. Deleting a reopened word completely and typing a new one in the same place carries it over (`resumeEmptiedBefore`).
- **Editing inside a word** (letters after the cursor): characters are committed directly, with no composing and no autocorrect, and the edit is tracked in `editOriginal`/`editCurrent`. It ends when the cursor leaves the word, or at a separator typed at the word's end.
- **Learning** (`learnFromEdit`): if the old word was a recent autocorrection (`recentCorrections`: corrected → typed) and the person restored what they typed, that word is confirmed. Otherwise, if the source (the typed form, or the old word) is unknown, the new word is known, and they're within `closeEnough` (≤2 edits, ≤ a third of the length), `UserModel.learnCorrection(source, new)` stores it. `TapDecoder` applies a stored fix before anything else. Keeping the typo (`confirm`, e.g. backspace-undo) deletes the fix.
- **Deleting:** plain characters (below U+0300) are deleted with `deleteSurroundingText` so the text is current immediately; emoji, other characters and deletes in an empty field use a DEL key event.
- **Double-space period:** off by default; `doubleSpaceBlocked` is set by backspace and cleared by any other character.

## Emoji search

The panel's magnifier calls `onEmojiSearch`: the letters come back, `searching` routes keys into `searchQuery` (delete with an empty query returns to the panel, enter or ✕ closes), and `EmojiSearchBar` shows results above the keys. The IME window grows by the bar's height while it's open. Ranking (`EmojiSearch`): name-word match beats keyword match, whole word beats prefix; then recently used, Unicode's 2021 top-10 most-used emoji, shorter names, CLDR order. `EmojiData.KEYWORDS` entries are name words, `~`, keywords. The suggestion strip is hidden while searching (`KeyboardView.setStripVisible`).

## Measured results (simulated input, desktop JVM)

From `tools/run_tests.sh`, with tap noise σ = 0.30 key widths and 400 words sampled by frequency:

| Check | Result |
|---|---|
| Correctly-hit words left alone | 259/273; 0 correctly typed words changed. The 14 misses are noise-hit words, some changed into other real words |
| Typos fixed (swap, drop or double letter) | 102/127 (80%) |
| Swipe: intended word first | 375/400 (94%) |
| Swipe: intended word in top 3 | 392/400 (98%) |
| Speed | about 5 ms per tap decode, about 4 ms per swipe decode, on a desktop CPU |

Simulated swipes are cleaner than real ones, so expect lower real-world swipe accuracy. The tuning parameters (`shapeWeight`, `endWeight`, `priorWeight`, and the first-letter threshold of 3.0) were picked by sweeping in `Sim`.

## Known gaps and risks

1. **On-device speed is unknown.** Both decoders run on the UI thread at every keystroke. A phone can be several times slower than a desktop JVM; if typing lags, move decoding to a background thread and post results back.
2. **No bundled next-word model.** Predictions come only from learned pairs, so the bar is empty after a space until the user has typed for a while.
3. **No live swipe preview.** Gboard shows the word while you're still swiping; this keyboard shows it only after you lift your finger.
4. **Learned tap offsets affect taps only, not swipes.**
5. **Swipe vs. tap detection:** a touch becomes a swipe after 0.6 key widths of movement, or 1.2 within 300 ms of the last tap (to protect fast typing). A swipe that decodes to nothing is typed as a tap on the start key. These thresholds are guesses and need real-finger tuning.
6. **Emoji panel:** no skin tones. Emoji the phone can't draw are hidden, so older phones show fewer.
7. **Tests use the JDK, not Gradle:** `tools/` uses plain javac/java with stubs. Porting `FlowTest` scenarios to JUnit (`app/src/test`) with real Android classes would need Robolectric, which isn't set up.
8. **targetSdk 34 is deliberate:** it avoids Android 15's enforced edge-to-edge layout for the keyboard window. The app isn't meant for the Play Store.
9. **The committed `debug.keystore` is deliberate:** builds from any machine or CI install over each other without wiping learned data. It isn't a secret.
10. **Licensing:** the word list comes from wordfreq data (CC BY-SA 4.0), filtered with Hunspell en_US/SCOWL. The offensive-word flags come from better_profanity (MIT). The credits are in the About section of the settings screen.

## History

1. **Dictionary:** built with `tools/make_dict.py`. The first version, raw wordfreq output, contained misspellings like "teh", which would have stopped autocorrect from fixing them. Filtering through Hunspell fixed that.
2. **Engine:** written and tuned with `Sim`. Adding a doubled-tap insert cost and allowing a swapped first letter raised typo fixes from 93 to 102 of 127. Pruning against the top-k threshold made tap decoding about 35% faster with identical accuracy.
3. **Android app:** service, view, emoji panel, themes and settings written, then compiled against the stubs.
4. **Fixed two bugs found by `FlowTest`:**
   - The keyboard service overwrote its lexicon with null when a text field opened.
   - Shift state wasn't recomputed after an automatically inserted space, so a word swiped or typed after ". " wasn't capitalized.
5. **APK not built:** the earlier session couldn't reach Google's Maven, Gradle or SDK servers, or the user's GitHub. That's why the project moved to Claude Code with a GitHub repo.
